# 调研流程：钉版本、核断言、留台账

调研的产出不是文章本身，是**一份可核查的事实台账**；文章只是台账的发布视图。顺序不能反：先核后写，写的时候每个断言都能指回台账。

## 1 · 钉版本

- 优先最新 **release tag**，不拿 main 当发布口径；记录 tag 名与 commit。README 描述的可能是 main，代码行为以 tag 为准，两者不一致本身就是一条可写的事实。
- 配套物版本单独记：镜像 tag、插件/扩展版本、依赖的运行时版本。「主程序 v2.2 配套插件还是 v2.0」这类版本脱节是高频反直觉点。
- 调研中途上游发新版：不追。文章口径钉死在开工时的 tag，脚注写清。

## 2 · README / 官网断言逐条核

把 README 和官网首页的功能声明列成清单，逐条标记：

| 标记 | 含义 | 处理 |
|---|---|---|
| 已核实 | 源码或运行证据支持 | 正文可写，带版本锚 |
| 未核实 | 没跑到/没读到 | 不写，或明说「文档声称」 |
| 证伪 | 源码/运行结果与声明矛盾 | 反直觉论点的富矿，重点展开 |

- 机制类断言必须落到源码（研究阶段记 `path:line`，**行号只留在台账，正文不写**）或运行证据（输出、落盘文件、日志）。
- 他人博客/评测的未验证说法先核再写。性能声明尤其如此：官方 benchmark 的测试条件往往和读者环境差几个量级。
- 配置项语义去源码核，不抄文档：缺省值看解析分支与构造器回填，执行条件看「这个键在什么前提下才被读」（铁律 9）。

## 3 · 本地跑通

- 先跑官方最小示例（quickstart），确认安装路径可行；再跑文章要讲的场景。
- 装不上/跑不通如实记录原因（依赖冲突、平台限制、硬件门槛），文章里如实说——「哪些环境用不了」对读者比成功路径更有价值。
- 实验产生的命令与输出**当场存台账**，别指望写作时还能复现一模一样的读数。

## 4 · 事实台账

工作区 `notes/<tool>-facts.md`，按主题分节，每条事实带出处：

```markdown
## 配置语义
- `--max-batch` 缺省 8：`config.py` 的 `load()` 里 `args.max_batch or 8`（path:line 记这里）
- 证伪：README 说支持 X，v0.9.2 源码里 X 分支直接 raise NotImplementedError

## 运行读数
- 命令：`...`；输出：`...`（原样贴）
```

正文从台账取结论 + 版本锚 + 标识符名；`path:line` 永不进发布稿（铁律 7）。

## 5 · 证据通道（按工具类型选）

铁律 8 要求每个实操 Step 有「看得见效果」的证据。不同工具的可见通道不同，起草前先对号：

| 工具类型 | 首选证据 | 补充通道 |
|---|---|---|
| CLI 工具 | 命令 + stdout/stderr + 退出码成对贴 | 产物文件（`cat`/`ls -l` 回读）、`--verbose`/`--dry-run` 输出 |
| 库 / SDK | 最小可运行代码 + 执行输出 | 返回值结构打印、副作用回读（写出的文件、改掉的记录） |
| 服务 / 推理框架 | API 入参 + 响应片段成对贴 | 服务日志、metrics 端点、落盘配置 |
| MCP 服务器 | `tools/list` 清单 + `tools/call` 入参返回值 | 服务器日志、客户端侧实际生效截图 |
| Agent skill | 触发场景 + 装前/装后同一任务的行为对照 | skill 实际加载的证据（会话里可见的指令生效点） |
| Web UI 产品 | 元素级截图（铁律 6） | 截图 + 该步的落库/落盘形态 |

两条通用配方：

- **回声/假服务**：断言「中间层到底改了什么字节」时，日志和最终回答都反推不出来。把下游临时指向一个只回吐自身收到的请求体的假服务，跑完切回。多个出网调用混在一起时，靠 Host/端口/记号（`<absent>`、`N chars`）分辨每次调用是谁发起的，正文开头把记号约定清楚。
- **单变量对照组**：多个组件/开关互相覆盖时，只换一格、读数并列贴；全开终态收在最后一步当验收。

## 6 · 性能数字的呈现（推理框架类重点）

- 吞吐/延迟/显存占用必须带测试条件：模型与参数量、量化方式、硬件档次（如「16 GB 内存的 x86 Mac」「单张 24 GB 显卡」）、并发/批大小、输入长度。条件写一次（脚注或表格头），不逐条重复。
- 单次跑的数字不下结论；至少三次取中位数，或明说「单次采样」。
- 不写「我这台跑不跑得动」的元叙事（铁律 1）；写「在 <条件> 下，吞吐为 <读数>」的产品事实句式。
- 官方 benchmark 与自己读数并列时，先对齐条件再比；对不齐就只引官方数字并注明条件，不硬比。
