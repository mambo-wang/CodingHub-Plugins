# 证据纪律

评测长文的可信度全在证据分级上。写之前建台账，写完对账。

## 台账格式

`facts.md` 里每条一个二级标题，正文用 `[E01]` 引用：

```markdown
## E07
- claim: 索引 196 个 Python 文件耗时 3.2 秒
- source: `command: codewiki index --repo D:/repos/X (exit 0)`
- observed: `indexed 196 files in 3.2s`（终端原文）
- strength: measured
```

`source` 三种写法，选一种：

| 写法 | 用于 |
| --- | --- |
| `command: <完整命令> (exit <码>)` | 本机跑出来的 |
| `file:<绝对路径>:<起-止行>` | 读源码得到的 |
| `url: <链接>` | 对方文档 / README / 官网 |

`observed` 贴实际看到的原文，不要转述成形容词。写"输出里有 `no such file`"，不写"报了个错"。

## 四种 strength

- `measured` — 本机跑出来的，有命令和退出码。
- `read-code` — 读源码得到的，有 `文件:行号`。
- `author-claim` — 对方自称。正文必须写成"声称/README 说"，不能写成事实。
- `inferred` — 你从代码或行为推的。正文必须留推测语气（可能、尚未验证、看起来）。

只有前两种能支撑判断句的主语。后两种要么归因，要么降级。

## 降级表（来自 `scientific-humanization`，工程评测里的对应形式）

| 不能写成 | 应该写成 |
| --- | --- |
| 增量检索比全量重建快 40% | 增量路径只重建受影响模块；文中未给出实测数据 |
| 支持二十种语言 | README 列了二十种语言；本次只测了 Python 和 Go |
| 并发安全 | 单进程下未观察到冲突，并发行为未测 |
| 能防止文档失真 | 检查器报告引用与代码的偏离，是否算失真仍需人工裁决 |
| 效果显著 | 给出前后两份原文输出，让读者自己判断 |
| 离线可用 | 在断网条件下跑通了 X；Y 仍需联网（截图 07） |

规则：命中就把强说法降级，而不是换个说法继续说满。

## 未测就写"未测"

对比章节最容易掺水。同一维度没有可比数据时，明确写"未测"，不要靠形容词补。表格里的空格也是信息。

## 读者测试怎么用台账

P5 开一个不带本次上下文的子 Agent，只喂 `draft.md`。问题清单里必须包含：

1. 这篇文章说它最好的地方是什么？依据在哪一句？
2. 哪些数字你找不到出处？
3. 只看图能否回答"数据从哪来到哪去"？
4. 有没有哪句话读起来像厂商文案而不像实测？

答错或答偏的位置就是缺口。补完再跑一轮，直到不再冒出新缺口。

## 交付前自查

- [ ] 正文每个 `[E##]` 在台账里存在，台账每条都被引用过。
- [ ] 没有 `author-claim` 被写成事实。
- [ ] 每个数字都能指回命令、`文件:行号` 或链接。
- [ ] 失败路径、报错原文至少各有一处。
- [ ] `node scripts/lint_article.cjs draft.md --wechat` 报 0 FAIL。
