# 文章结构

## 先判 track

| 判据 | track |
| --- | --- |
| 要 clone / 装依赖 / 编译，或提供真实 CLI、库接口，跑起来才有结论 | **A** 读源码 + 安装实操 |
| 一行配置或一个目录拷贝就接进来，本体是提示词 / 工具清单 / 远端服务 | **B** MCP、Skill 这类拿来即用 |

判据看"结论从哪来"，不看语言或仓库大小。一个只有 `SKILL.md` 的仓库是 B；一个 npm 包但要读它的 schema 才能说清行为，是 A。

篇幅参考：A 类 6000–12000 字，图 2–3 张、截图 4–8 张；B 类 3500–7000 字，图 1–2 张、截图 3–6 张。

**白皮书式长文（默认）**：多组件组合、机制介绍、把一段实践总结成长文时走这套固定骨架：**导语口径**（引用块给版本 / 环境 / 条件）→ **0 这几样拼起来做什么**（一句话差异 + 三层定位）→ **1 各自是什么**（每个组件一段，配一张「定位 / 管什么 / 一句话差异」对比表）→ **2 工作原理**（2.1 全景 + 系统小节，每节结论前置）→ **3 实操走查**（Step 0..N，每步一条可见证据）→ **4 边界**（适合谁 / 不适合谁 / 没验到什么）→ **附 台账对照**（编号段表 + 环境）。章节名不套模板，lint 用 `--track skip`。写法细则（一句话差异、加粗原则领起、诚实边界）见 [writing-style.md](writing-style.md)「白皮书式长文」。**旧的 C 类四段式（是什么 / 怎么工作 / 实操 / 小结）已退役**，仅存档于 [wechat-structure.md](wechat-structure.md)。篇幅参考：组合篇 6000–9000 字，原理图 4–6 张，截图按实操 Step 数。

**可读性（三类通用，尤其面向 mixed 读者）**：分层不降级。① 开头或第一节给一张术语速查表（核心词白话定义，后文不再解释）；② 每小节先一句白话结论、再展开支撑，机制节标注「赶时间可跳实操」；③ 砍重复论点与写作元说明（台账编号约定、版本锚方法这类挪附录），同一个论点全篇只立一次、证一次；④ 收束段用白话不堆标识符，但**深度与证据标识符保留**——白话化的是入口和收束，不是把机制删掉。细则见 [writing-style.md](writing-style.md)。

## A 类十节

| 节 | 写什么 | 证据要求 | 常见写坏 |
| --- | --- | --- | --- |
| 1 结论前置 | 它是什么、实测到什么程度、适合谁，三句 | 每句能指回台账（内联 `[E##]` 可选） | 写成广告导语；把"未测"的东西写进结论 |
| 2 工具是什么 | 形态、语言与运行时、许可证、仓库活跃度、维护方 | `file:` 指 LICENSE / package.json；`command:` 指版本行 | 抄 README 第一段 |
| 3 它解决谁的什么问题 | 目标用户 + 替代路径 + 不用它会怎样 | 替代路径要能点名 | 复述口号，不写"不用会怎样" |
| 4 工作原理 | 架构图 + 一条主路径的泳道/时序图；机制用版本锚 + 标识符名 + 运行证据，行号只进台账 | `read-code` | 只画框不标数据流；把 README 的模块名照抄成节点；正文写源码行号 |
| 5 安装与首次运行 | 真实命令、真实输出、版本、耗时 | `measured`，装失败也贴 | 只贴成功那一次；省略报错 |
| 6 实操 | 一个有对错的任务，不是 demo 脚本 | 截图 + 输出原文 | 用作者自带的样例数据自证 |
| 7 能力边界拷问 | 错误输入、超限、离线、并发、陌生仓库 | 至少三例，含失败 | 全写"表现良好" |
| 8 同类对比与踩坑 | 同维度对比；踩坑按现象→原因→绕法 | 没测的格子写"未测" | 拿不同维度拼成"更优" |
| 9 适合谁 | 给判断条件，不给评分 | — | 打分表代替条件 |
| 10 附录 | 环境版本、完整命令清单、台账编号对照 | — | 漏环境，别人复现不了 |

第 7 节是这篇的价值所在。前面写得再顺，只要第 7 节是空的，整篇就是软文。

## B 类八节

B 类没有编译和安装，把第 5、6 节换成接入成本和契约取证：

| 节 | 写什么 | 关键动作 |
| --- | --- | --- |
| 1 结论前置 | 它替谁省了哪一步 | 同上 |
| 2 它是什么、接入要多久 | 装进来几步、改了哪个配置、要不要密钥 | 贴真实配置，密钥脱敏成 `sk-***` |
| 3 工作原理：契约与调度 | 它靠什么生效：提示词、脚本、还是远端服务 | 读 `SKILL.md` / 工具清单 / 附带脚本，指出哪一段真正约束行为 |
| 4 实操：一个真实任务 | 原样贴触发语句与执行轨迹 | 截图关键节点，保留工具调用名和参数 |
| 5 拷问：它真按自己写的规则做了吗 | 把它的规则逐条当断言验 | 该问的问了没、该禁的禁了没、失败时停了没 |
| 6 替代方案与差异 | 差在哪一层：契约、脚本、还是模型能力 | 别只比功能表 |
| 7 适合谁 | 条件 | — |
| 8 附录 | 配置、版本、台账 | — |

第 5 节是 B 类的第 7 节。一个 Skill 说自己"强制先问再改"，就得真去开一个会话看它问不问；没问就是反例，写进去。

## 图与截图的落位

| 位置 | 内容 | 类型（一律走 `diagram-design`） |
| --- | --- | --- |
| §2 开头 | 部署 / 组件全景 | Architecture |
| §2 中段 | 一条主路径怎么走完 | Sequence 或 Swimlane |
| §2 缓存/分层节 | 多层查找、容量折损 | Layer stack 或 Data flow |
| §3 | 关键命令 / 页面的真实证据 | `capture_cli.cjs` 终端卡、`web-shot.mjs` 元素级截图 |
| §4 | 失败输出原文 | 终端卡，exit 码必须可见 |

原理图统一用 `diagram-design` 出：`self_check.py` 过检、`export_png.py` 出 @2x PNG 落 `imgs/`，图源 `.html` 落 `diagrams/`，图注 `图 N｜一句话`。**不要用 `render.py` / `mermaid2png.py` / `fig-template.html` 旧出图法。** 一张图只讲一件事，节点超过 9 个就拆总览 + 细节。
