# 调度细则：P0–P6

四个 skill 管四件不同的事，顺序错了会返工。本 skill 只做调度，具体规则在各自的 skill 里，用到时再加载。

| 阶段 | 干什么 | 加载谁 | 产出 |
| --- | --- | --- | --- |
| P0 | 取材建台账，不写正文 | 无（`capture_cli.cjs`） | 仓库/配置、命令清单、`facts.md` ≥15 条 |
| P1 | 澄清提问 + 定 track | `doc-coauthoring` Stage 1 | 5–10 问的答复；track A/B 判定 |
| P2 | 搭骨架 + 逐节填充 | `doc-coauthoring` Stage 2 + `scaffold.cjs` | `draft.md` 全文字 |
| P2.5 | 每节写完立刻校证据强度 | `scientific-humanization` | 降级后的判断句 |
| P3 | 出图 | `diagram-design` | `diagrams/*.html` + `@2x.png` |
| P4 | 截图 | `screenshot-guide.md` | `shots/*.png` |
| P5 | 读者测试 | `doc-coauthoring` Stage 3 | 缺口清单 → 回 P2 补 |
| P6 | 通稿润色 | `humanizer-zh` | 定稿 |
| P7 | 收口校验 | `lint_article.cjs` | 0 FAIL |

## 为什么是这个顺序

- **P0 在 P1 之前**：没跑过工具就提问，问出来的是 README 的复述，不是边界情况。先拿到 `--help`、真实报错、版本行，提问才能命中"离线怎么办、超限怎么办"。
- **P2.5 穿插在 P2 里，不等全文**：性能说法一旦写进正文并被后文引用，后面降级要改一串地方。每节写完当场校。
- **P3 在 P2 之后**：图的节点跟着段落划分走。段落改了图就要重画——这是实测过的返工。
- **P4 可以和 P3 并行**，但两者都必须在 P6 之前。
- **P6 必须最后**：`humanizer-zh` 会删"预告下文"的句子，结构没定时删掉的可能是下一轮要用的位置。

## 三条硬约束

1. **每个数字回台账。** 正文里的数字、耗时、行数、百分比必须能在 `facts.md` 找到同编号的条目，`lint_article.cjs` 会查。
2. **README 的自评只能以"声称"出现。** `strength: author-claim` 的条目被引用时，那句话必须带归因词（声称 / README 说 / 官方文档写 / 标称）。
3. **失败也是内容。** 装不上、跑崩、超时的原样输出进正文和截图，不删。评测文章里只有成功路径等于没测。

## 与 `oss-tool-eval` 的关系

如果本机装了 `oss-tool-eval`，它覆盖的是 P0 和 P4 的工程取证腿（下载源码 → 安装 → 读 CLI 契约 → 实操）。本 skill 是它外层的调度与写作腿：结构、证据纪律、图、读者测试、润色。两者不冲突，按上面的阶段表各用各的；不要在同一份稿子里两套流程并行跑，会写出两份互相矛盾的台账。

## 跳步的代价（真实观察）

- 跳过 P1 直接写：结构会写成"功能罗列"，缺"不用它会怎样"。
- 跳过 P2.5：出现"比 X 快 40%"这种没跑过的数。
- 跳过 P5：作者自己的前设留在文中，读者读到才发现缺一步。P5 用无上下文子 Agent，问题里必须包含"只看图能否回答 X"。
