# 文风与禁则

## 人称与语气

- 用「你」直接称呼读者；「我」只出现在**判断句**里（「我认为最被低估的是它的调度器」「我对『开箱即用』这个说法是持保留态度的」），不写「我试了一下」这类流水账。
- 承认不确定性：「这类差异本身不致命，致命的是数量级」「排查时别以为是上游挂了」。
- 开头可用设问引段：「想知道一个人是不是真的理解这个工具，问他这个问题就够了」——全篇不超过一处。
- 短句为主，长短交错；先结论后展开。段尾不要都收成感叹式总结。

## 可读性：兼顾小白与简洁（分层不降级）

长文最容易犯的两个毛病：术语不解释（小白卡在机制节）、论点和元说明反复出现（读着啰嗦）。修法不是删深度，是分层：

- **术语速查表**：核心词在开头或第一节给一张白话定义表（如 token / KV 缓存 / prefill·decode / 路由 / 消费者 / 插件），后文不再解释。判据：没读过前文的人能看懂这张表。
- **结论前置**：每小节先一句白话结论、再展开支撑；机制节开头标一句「这节偏机制，赶时间可直接跳实操」，给小白一个跳过入口。
- **砍重复与元说明**：同一个论点全篇只立一次、证一次，别在导语 / 正文 / 小结 / 结尾各立一遍；写作约定（台账编号怎么用、版本锚 + 标识符的方法）挪进附录，不占正文。
- **分层不降级**：白话化的是入口（速查表 / 结论句）和收束段，不是把机制删掉。深度小节保留证据标识符（函数名 / 字段名 / 配置键），小白可跳过、工程师能核对。**立场那句（反直觉论点）原样保留，不为通俗稀释。**
- **数字给白话框**：精确值旁边补一句量级白话（「约 36 KB/token」「一个 chunk 约 9 MB，搬过网线几十毫秒、重算烧整张卡」），再放精确读数。
- **减幅有底线**：图和证据本身撑篇幅，别为凑短删证据链；砍的是重复和元说明，不是事实。

## 白皮书式长文（默认写法）

默认长文按这套写（token-factory 组合篇即样板）：冷静、结论前置、用对比表代替罗列、边界写到诚实。

- **导语只留口径**：一段说清「它把什么变成什么」，再用引用块给版本/环境口径。台账编号约定、版本锚方法、图源路径这类写作元说明挪进附录，不进导语。
- **先结论后支撑**：每节第一句就是结论（一句白话），后面才是支撑与数字；机制节开头标「赶时间可直接跳到实操」。
- **一句话差异**：介绍多组件时，给每个组件一句「把 X 变成 Y」的差异句，比功能清单好记；再配一张「定位 / 管什么 / 一句话差异」对比表。
- **加粗原则领起**：小节结论用加粗领起（「**第一，…**」），但加粗只给结论与立场句，不整段加粗。
- **对比表代替长段**：三者以上、多维度、平行可比时用表格；两两比较用行文。
- **诚实边界**：单列「适合谁 / 不适合谁 / 这篇没验到什么」；没跑过的性能当「声称」读并写清测试条件；不回避失败与缺口。
- **图注统一 `图 N｜一句话`**：图是 `diagram-design` 出的编辑风，图注一句话点出「这张图要让读者记住什么」，不与正文重复。
- **收束用自检问句或一句话总结**：如「打开 X 页是空的，说明 Y 没做吗？」——用来检验读者是否真读懂，不作抒情。
- **去元说明**：同一论点全篇只立一次，不在导语/正文/小结/结尾反复重申；不写「本文将带你…」这类写作过程说明。

## 数字与事实的呈现（铁律 1 的执行细则）

| 场景 | 错误写法 | 正确写法 |
|---|---|---|
| 版本事实 | 我拉下来一看是 0.9.2 | 最新 release v0.9.2 配套的扩展还停在 0.8 |
| 分支对比 | 本机把两个分支都翻了一遍 | v0.9.2 和 main 分支完全一致 |
| 机制断言 | 我实测覆盖没有开关 | 翻遍 v0.9.2 和 main 两个分支：**这个覆盖没有开关** |
| 运行读数 | 我在日志里看到顺序是 | 落盘后的配置长这样（给表格）……顺序不是随手定的 |
| 性能数字 | 我这台跑出来 40 tok/s | 在 <硬件档次/模型/量化/并发> 条件下，吞吐为 40 tok/s（条件写一次） |

- **正文不写源码行号**。研究阶段照旧记 `path:line`，那份定位留在事实台账里，发布稿只说行为。出处这样给：版本锚（「v0.9.2 的源码里」）、标识符名（`load_config()`、`default_batch = 8` 这类原样引用的代码片段）、文件级线索（`server.py`）、运行证据（命令输出、落盘文件、日志读数）。文末引文写「行为核对了 v0.9.2 tag 源码」，别写「行号可直接对」。
- 禁词族：本机、实测（作叙事主语时）、我这台、跑得动、吃掉多少内存。写完后 grep 复查。

## 语言细节

- 简体中文；全角标点；中文与英文/数字/代码之间留一个空格。
- 引号用「」和『』；行内代码、字段名、命令、工具名一律反引号。
- 破折号节制使用（全篇两三处以内），优先拆成短句或冒号。
- 粗体只给两处用：关键结论、专有名词首次亮出处。不要整段加粗。
- 无表情符号；图片不做花纹装饰。
- 术语口径全篇（系列则全系列）一致：同一个概念只用同一个词，别一会儿「实例」一会儿「副本」。
- **小结（和每一节的开场句）用白话，不堆标识符。** 正文里该出现的字段名、函数名照写；到了收束段就换成读者不查表也能懂的说法——日志字段 → 「账单」、内部挂起状态 → 「请求挂在那儿不动」、上游 Body → 「请求体」。判据：把这段单独发给一个没读过前文的人，他能说清「发生了什么、我该怎么防」。**立场那句（反直觉论点）原样保留，它是全篇唯一的加粗结论，不要为了通俗而稀释。**

## AI 味黑名单（初稿时避免，定稿时复查）

- 词汇：此外、至关重要、深入探讨、赋能、无缝、强大、织锦、宝贵、充满活力、值得注意的是、需要指出的是。
- 句式：不仅……而且……、这不仅仅是……而是……、从 X 到 Y（虚假范围）、作为/标志着/见证了。
- 结构：三段式排比、段段「首先/其次/最后」、结尾「希望这对你有帮助」。
- 定稿前可选跑一遍 `content-humanizer` skill 自查（目标 ≥40 分；注意它的 `--score` 是 stub，量化要手工做）；它的通用规则不认「我」的判断句——那是有意保留的个性，不要为凑分删掉。

## 坑的写法

- 坑只出现在咬人的那个步骤，用 blockquote callout；不单开「踩坑记录」章节。
- 普通坑给规避动作，语气口语：「别顺手改成 `true`」。
- 危险坑讲爆炸半径（泄露的是什么、毁掉的是什么），并给出正确顺序建议。
- 小结里用一句话把全部坑点名回顾。
- **失败进正文**：装不上、跑崩、超时的命令与原始输出如实贴。只有成功路径的调研等于没测。

## 脱敏（发布前逐项核）

| 项 | 要求 |
|---|---|
| API key / token | `sk-****`（截图里也要涂掉，真实前缀如 `sk-6**********（已略）` 属泄露） |
| 演示凭据 | 显式占位符（如 `sk-demo-local`），真实凭据不得出现 |
| 局域网 IP | 不出现（`10.x.x.x`、`192.168.x.x`） |
| 主机名/用户名 | 不出现（终端提示符、路径里的用户名） |
| 本机路径 | 不出现 `/Users/...` |
| 截图逐张扫描 | 凭证格子 / 终端提示符 / 浏览器地址栏与书签 / 右上角账号标识 / 监控面板变量框 |
