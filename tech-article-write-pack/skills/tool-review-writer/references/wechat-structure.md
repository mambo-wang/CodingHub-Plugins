# 文章结构模板（四段式）

> **遗留·已退役（2026-11-23）**：本四段式来自 `wechat-tool-review`，现役默认是「白皮书式长文」，结构见 [article-structure.md](article-structure.md)。本文件仅存档，不再作为默认骨架。

骨架从《Higress AI 网关全解析》第 01 篇定型，泛化到开源工具调研。只换内容不换骨架。

**系列篇定位（动笔前）**：读工作区的系列地图（若有），取本篇主题、核心论点、与相邻篇的衔接；读前一篇成稿，兑现旧文留下的预告。单篇则确认工具名、要钉的版本、读者预设（写给谁、他已会什么）、有没有对比对象。

## 骨架总览

| 部分 | 做什么 | 占篇幅 |
|---|---|---|
| 标题 | 系列 `# <系列名> NN｜<副标题>`；单篇 `# <工具名>：<副标题>` | — |
| 导语 | blockquote 三段：系列说明（或单篇定位）/ 本篇讲什么 / 版本与环境口径 | ~150 字 |
| 一、是什么 | 官方定义拆解 → 解决什么问题、生态位 → 总纲图 → 亮出判断 | ~25% |
| 二、怎么工作 | 机制分组 → 原理图（≥1 张）→ 反直觉小节（核心论点落点） | ~35% |
| 三、实操 | Step 0..N 分步 + 坑 callout + 证据 + 验证 | ~30% |
| 四、小结 | 底座回扣 / 本质一句 / 坑回顾 / 适用边界 / 导读表（系列）/ 互动 | ~10% |
| 脚注 | 来源 + 版本口径 + 脱敏声明（性能文加测试条件） | 1 段 |

## 标题与导语

- 副标题用「主题：并列关键词」格式，如 `# vLLM：调度器怎么把吞吐做上去的`。
- 导语三要素（句式可套，内容替换）：

```
> 「开源工具拆解」系列结构固定：先讲清这个工具是什么、解决什么问题，再拆开它的工作原理，最后动手跑一遍。
>
> 本篇是 <工具名>：**它是什么、核心机制怎么运转、以及从零把 <场景> 跑通一次**。
>
> 全文基于 <tag/版本>，安装方式为 <pip/docker/源码编译>；文中的配置和命令都基于这个版本。
```

单篇把第一段的系列说明换成一句选题动机（为什么现在值得看这个工具）。

## 一、是什么

两种开篇任选：**官方定义开篇**（引 README/官网一句话定义 → 拆开逐段解读）或**问题开篇**（直接讲它解决什么痛点、没有它时大家怎么凑合）。段落节奏：短段 + 每段一个 bold 首句。

必备元素：

1. **官方定义拆解**（引原句，概括不搬运；README 的自评只能以「声称」出现，核实过的才写成事实）。
2. **生态位**：它替代谁、和谁搭配、和最近竞品的分界线在哪。有官方归纳的核心优势就逐条过，指明哪条信息量最大并展开。
3. **总纲图**：能力地图或组件全景；系列后续篇目在这张图上标注本篇新增部分，读者建立连续心智。
4. **亮判断**：「最被低估的是……最被高估的是……」这类立场句，并说理由（讲清判断标准，不是抛观点）。

## 二、怎么工作

- 开头先给**全局分组**（bullet：谁管什么、各一段话），再分小节展开。
- **至少一张原理图（硬要求）**：分层/组件关系用**架构图**，一条数据路径用**流程图**，跨方向或跨时间的协作用**时序图**；图贴着对应机制小节放，配一句过渡说明「这张图在讲什么」。画法分工见 `toolchain.md`。
- 小节两种视角：**使用者视角**（「你敲下命令/发出请求时发生的事」）或**数据视角**（「一条数据穿过……」）。
- 机制事实必须带出处：版本锚 + 标识符名 + 运行证据（铁律 7 的三样），直接放正文，脚注不重复。
- **反直觉小节**是本段高点：核心论点落在这里，格式为「三个假设 / 三个误解 / 两个词要分清」这类可数结构。调研里核出的「README 说错了/没说」优先放这里。
- 需要对比时用表格（与竞品、开/关某机制的行为差异、参数语义）。表格信息密度高，一个足够。

## 三、实操

- 开头两句：命令可直接抄 + 版本/入口口径 + 与原理图对照看的总述（「前四步在搭环境，第五步才打开核心开关」）。
- 步骤格式：`**Step N · 动作**` 单行加粗标题，正文 = 动作描述 + 命令/配置片段 + 证据。
- Step 0 通常是安装与环境确认（版本命令 + 输出成对贴）；随后最小跑通 → 文章主题场景 → 验证步。
- **坑写成 callout**（blockquote，就放在咬人的那一步）：
  - 普通坑：一两句，直接给规避动作（「`--flag` 默认关着，别以为装了就有」）。
  - 危险步骤：标注「**这里是全文最危险的一步**」，讲清爆炸半径和正确顺序。
- 每步给「跑完后长什么样」：产物文件、落盘配置、服务状态，带注释的片段。
- **贴出来的配置逐键交代**（铁律 9）：控制什么 / 缺省值 / 写错漏写的后果，三类事实回源码核；最优先查「配了但运行时不读」。写法用标识符名 + 缺省值 + 后果，不写行号。
- **每步必须有一份「看得见效果」的证据**（铁律 8）：命令 + 期望输出成对出现，输出原样贴进代码块，别只写「这时你会看到……」。证据通道按工具类型选（`research.md` 第 5 节）：CLI 输出 / API 入参返回值 / 日志读数 / 产物回读 / 元素级截图。
  - 断言「中间层到底改了什么」时搭回声/假服务取证，记号约定写在前头。
  - 多组件互相覆盖时给**单变量对照组**（只换一格，读数并列贴），全开终态收在最后一步当验收。
- 验证步放最后：别只看界面/退出码，看数据面（产物内容、落盘配置、服务端读数），并给出习惯建议。
- 收尾：对象清单（这些命令最后变成了什么）+ 一个跨篇预告句（系列）或延伸阅读方向（单篇）。

## 四、小结

三段 + 表 + 互动：

1. **底座回扣**：核心技术选型两三样，各自决定了什么性格。
2. **本质一句**（加粗，全篇唯一的加粗结论）：一句话说清这个工具把什么东西从什么变成了什么。
3. **坑回顾**：一句话列出全部坑名，说它们散布在哪些步骤。
4. **适用边界**：什么时候该用它、什么时候不该（硬件门槛、规模门槛、场景错位）。调研文的增量价值一半在这里。
5. **系列导读表**（系列才有）：序号 | 主题 | 核心问题，本篇行加粗标「（本篇）」。
6. **互动句**：欢迎评论 + 抛一个开放问题（最好挑一个自己持保留态度的判断）。

## 脚注

单段 `*…*`，三件事齐全：来源（官网/仓库链接 + 源码 tag 核验 + 配置来源）、版本口径、脱敏声明。性能文加测试条件。样本：

```
*产品定位引自官方 README；机制断言核对了 v0.9.2 tag 源码，运行读数来自同版本的本地部署。吞吐测试条件：7B 模型、4-bit 量化、单并发。示例中的 API Key 已脱敏。*
```

## 图注与编号

- 原理图 alt：`图 N：标题`（N 是按全文出现顺序的展示号，与文件名无关）。
- 截图 alt：`界面：动作`，描述自足（微信不渲染 alt 成图注）。
- 图放正文里就近；截图紧跟对应 Step 的配置/命令片段。
- 段间分隔：`## ` 大节之间用 `---`；小节之间不用。
